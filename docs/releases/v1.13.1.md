## Why this release

The library scan recognises a renamed or moved photo by a fingerprint of
its contents, taken from the start of the file and its size. When it finds
a match, the photo keeps its record, with its tags, people, faces and search
data.

Writing tags into a photo changes the start of the file, which is where
embedded metadata lives. Every write recorded the photo's new size and
modification time but not its new fingerprint. After any "Write all tags",
"Publish all", single-photo write, restore or repair, the stored fingerprint
no longer matched the file. If such a photo was then renamed or moved, the
scan did not recognise it. It removed the old record and created a new,
empty one, so the photo lost its tags, confirmed people, faces and search
data.

## What changed

- **Writes keep the fingerprint current.** Every operation that rewrites a
  photo now stores the file's new fingerprint along with its new size and
  modification time.
- **Moved photos with an outdated fingerprint are still recognised.**
  Photos written by earlier versions still carry an outdated fingerprint.
  When a photo's fingerprint finds no match, the scan also compares size and
  modification time, both of which a rename or move keeps exactly. A missing
  photo and a new file are treated as the same photo only when that pair is
  unique on both sides. If two files share a size and time, no guess is
  made.
- A recognised photo takes the current fingerprint of its file, so the next
  move is recognised directly.

## Verified

- Full test suite, all passing, run on a clean copy of this release.
- New test: a photo whose stored fingerprint is outdated is renamed from
  `.jpg` to `.png`. The scan keeps its record, records the `.png` type, and
  stores the file's current fingerprint. Two other files with identical
  size and modification time, both renamed, are not matched to either
  record.
- New test: after tags are written into a photo, the stored fingerprint
  matches the file.
