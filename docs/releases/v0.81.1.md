## 0.81.1 — 2026-08-29

Running the test suite was corrupting the user's real `library-state.json`,
replacing the configured library root (`C:\Dropbox\Photos`) with a temporary
test directory.  This caused the server to start up pointing at an empty or
nonexistent library — appearing as a "test server" with no photos.

### Root cause

`library_config.LIBRARY_STATE_PATH` is evaluated at import time from
`settings_path()`, which reads `LENSLEDGER_DATA_DIR`.  The test setUp patches
that env var *after* the module has already been imported, so the module-level
constant still points at the real config file.  Every call to
`save_library_state()`, `associate_db_path()`, or `_save_db_mappings()` during
test execution wrote test data to the user's real config.

Two specific tests also had direct issues:
- `test_onboarding_page_shown_for_true_first_run` deleted the real
  `library-state.json` and never restored it.
- `test_reconnection_page_shown_when_library_known_but_database_empty` called
  `save_library_state()` with a temp directory path on the real file.

### Fix

Added `patch.object(library_config, "LIBRARY_STATE_PATH", ...)` and
`patch.object(library_config, "LIBRARY_DATABASE_ROOT", ...)` to the test
class's `setUp`/`tearDown`, redirecting all library-state operations to the
temp directory for the duration of each test.  This covers all code paths —
the server handler, scan callbacks, and the two specific tests — without
needing per-test patches.

Also deleted a stray empty `photo_index.db` that a previous test run left in
the project directory.

## Verified

- Test suite: 88 tests passed
- After running tests, `library-state.json` still points at `C:\Dropbox\Photos`
  (previously it would be overwritten with a temp path)
