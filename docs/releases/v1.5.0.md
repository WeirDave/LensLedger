## Why this release

LensLedger decided where its own data lived the moment it started, and then
never reconsidered. Settings, the record of known libraries, the safety copies
taken before writing to a photo, and the auto-import log were all fixed to one
location at startup. Anything that pointed somewhere else afterwards still read
and wrote the original.

That is invisible in ordinary use, and harmful the moment it is not. A second
instance started against a different folder still changed the settings and the
library list of the first. Trying something out in a scratch copy could reach
back into the real one.

Every one of those paths is now worked out when it is needed, and there is a
supported way to run LensLedger against a folder of your choosing.

## Running against a different folder

A new option keeps everything LensLedger writes in a folder you name:

```
python src/photo_search.py --data-dir "D:\LensLedger Test"
```

Settings, safety copies, logs and the record of known libraries all go there
together. Nothing half-escapes into the usual location, which is the point —
it is the difference between a scratch copy and a scratch copy that quietly
edits the real one. The folder in use is logged at startup when the option is
given.

This pairs with the existing `--root` and `--db` options, which choose the
photo folder and the database.

## What was fixed

- **Settings** were read from and written to wherever LensLedger first looked.
- **The record of known libraries**, which holds the current library and every
  library ever added, had the same problem. A second instance could add its
  library to the real list, or change which library the real one opened next.
- **Safety copies** taken before writing to a photo went to the original
  location regardless of where the rest of the run was pointed.
- **The auto-import log** was fixed at startup in the same way.
- **Command-line tools** — the database utilities, the meaning-search indexer
  and the folder-tag generator — chose which database to use before reading
  their own options, so naming a database on the command line was decided
  against a location worked out earlier.

## Verified

- Full test suite: 160 tests, all passing, on Python 3.12.10 — up from 156.
- A new test walks every source file and fails if any module works out a
  data-folder path at load time rather than when it is used, naming the file
  and line. Reintroducing the original fault was confirmed to fail this test.
- A second test sets the data folder after everything has loaded and checks
  that thirteen separate paths follow it, including settings, the library
  record, the safety copies and the auto-import log.
- Two further tests confirm that saving settings and recording a library
  actually write inside the chosen folder rather than somewhere else.
- Checked in a browser against a library of generated test images: a full pass
  of location scanning, text recognition, meaning search and writing tags, with
  the safety copies landing in the named folder and the untouched locations
  confirmed unchanged afterwards.
