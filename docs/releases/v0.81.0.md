## 0.81.0 — 2026-08-29

The "Confirm all remaining" feature in People review was running an unbounded
loop that recomputed the centroid and re-scanned all candidates every round.
With many confirmed faces (e.g. 3,000+), the centroid barely shifted per round,
so each iteration found only a handful of new matches just barely crossing the
0.65 threshold.  This turned what should be a fast bulk operation into a slow
drip-feed — 24+ rounds of 4 confirmations each, taking several minutes.

### What changed

**Server (`confirm_remaining_faces`):**  After each round, the new count is
compared against the first round's count.  If it falls below 10% of round 1
(or fewer than 10 absolute), the loop stops early — the centroid is stable and
the remaining borderline faces need human review to produce a meaningful
centroid shift.

**Client (`faces-review.js`):**  When confirm-remaining stops early
(`needs_review` flag in the done event), the UI now calls `/api/faces/find-more`
to load the remaining borderline matches for human review instead of showing
a "done" status.  This keeps the human-in-the-loop workflow intact: the user
reviews borderline faces, the centroid shifts meaningfully, and the next
confirm-all round (if needed) will be effective.

### Why this approach

The iterative centroid-recompute loop serves a real purpose early in the naming
process: with few confirmed faces, each batch meaningfully shifts the centroid
and pulls new matches over the threshold.  But with thousands of confirmed
faces, adding 4 more moves the centroid by essentially nothing.  Rather than
lowering the threshold or capping rounds at an arbitrary number, the fix
detects when iteration has diminishing returns and hands the remaining work
back to the human — which produces better centroid updates anyway.
