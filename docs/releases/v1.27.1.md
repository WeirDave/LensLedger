# Meaning search holds its index in memory instead of rereading it

## What was slow

Every meaning (natural-language) search rebuilt its working set from scratch.
`semantic_index.search()` ran `SELECT ... FROM semantic_embeddings`, decoded
every stored vector back into Python floats, and scored the query against them
in a plain Python loop — and it did all of that again for each page of results,
because the viewer fetches meaning results a page at a time. On a large library
that is tens of thousands of vectors re-read and re-decoded on every keystroke's
worth of searching.

## What changed

The decoded embeddings are now held in memory and reused across searches and
pages. A search reloads them only when the index has actually changed, detected
by a cheap fingerprint of the embedding table (its row count and most recent
write) rather than by reading the vectors. When NumPy is present the vectors are
kept as one `(rows, dimensions)` float32 matrix and a query is scored as a single
matrix-vector product instead of a per-row Python loop — the same batched
approach the face-matching code already uses. Without NumPy, the original
pure-Python scoring still runs as a fallback, so the base install's behavior is
unchanged.

Search **results are unchanged** — the ranking is the same cosine similarity as
before, only computed faster. The in-memory copy is dropped and rebuilt
automatically after an indexing run adds or replaces vectors, so a search never
returns stale results.

This is an internal performance change. There is no new setting, no schema
change, and no change to how meaning search is set up or used.

## Not addressed here (noted for later)

The optional model is still reloaded for each search call when no encoder is
passed in, which dominates the cost of the first page of a meaning search.
Caching the loaded encoder across requests is a separate change with its own
memory trade-off and is left for a follow-up.

## Verified

- **Test suite:** `PYTHONPATH=src python -m unittest discover -s tests` — 465
  tests, all passing except 5 `test_server` metadata/people-publish workflows
  that require the bundled Windows ExifTool and already error on this Linux
  development machine (they pass on the Windows CI runner); the 5 were confirmed
  failing identically on `main` before this change.

  pure-Python scoring paths return the same ranking and scores, the other
  asserts the in-memory index is reloaded after the embedding table changes
  underneath it.
