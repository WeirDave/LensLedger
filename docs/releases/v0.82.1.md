## Context

The v0.81.18 release added a startup cleanup that clears stuck "broken data stream" scan errors so damaged JPEGs get retried with the tolerant decoder from v0.81.17. The cleanup was implemented inside `_configure_connection()` in `photo_index.py`, which runs every time any code path opens a database connection — not just at startup.

During heavy face-review sessions (naming and confirming many people), the database stays write-locked for extended periods while batch confirmations and confirm-all rounds run. Every concurrent HTTP request that opens a new connection tries to execute the UPDATE cleanup, hits the write lock, and crashes with `sqlite3.OperationalError: database is locked`. This caused repeated 500 errors for page loads during face review.

## What changed

The broken-data-stream cleanup in `_configure_connection()` now runs only once per process. A module-level `_broken_stream_cleared` flag ensures the UPDATE statements execute on the first connection and are skipped on all subsequent ones. The cleanup still happens at startup as intended, but no longer contends for write locks during normal operation.

## Verified

- Full test suite: 88 tests passed
- Reviewed the error traceback confirming the crash originated in the per-connection cleanup path
