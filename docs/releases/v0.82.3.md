## Summary

The "Open file" links in scan error dialogs (Photo locations, OCR, Meaning search, Face detection) silently failed when clicked — browsers block `file:///` URLs loaded from `http://` pages for security reasons.

## What changed

- **Server endpoint**: Added `/api/reveal-path` that accepts a relative path and opens the file's location in the OS file manager (Explorer on Windows, Finder on macOS, xdg-open on Linux). Includes a path-traversal guard to ensure the path stays within the library root.
- **Refactored**: Extracted the shared file-reveal logic from the existing `/api/reveal-file` (which takes an asset ID) into a shared `_reveal_on_disk` helper, used by both endpoints.
- **Frontend**: Changed the error list path links from `<a href="file:///...">` anchors to click handlers that POST to `/api/reveal-path`, which actually opens the file in the OS file manager.

## Verified

- Test suite: 88 tests passed.
- The `file:///` anchor and `target="_blank"` attributes are removed; the path link now calls the server endpoint on click.
- The server validates that the requested path is inside the library root before revealing it.
