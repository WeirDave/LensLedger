# Meaning search holds its index in memory instead of rereading it

## Why this release

- Every meaning (natural-language) search read the whole meaning index from the database, decoded every stored vector and scored the query against them one at a time. The photo viewer fetches meaning results a page at a time, so this was repeated for each page. On a large library that is tens of thousands of vectors per search.

## What changed

### Meaning search

- Meaning search is faster, most noticeably on large libraries and when paging through results. The decoded index is kept in memory and reused across searches and pages.
- The index is read again only after it has changed: a different number of indexed photos, or a newer write to it. The check reads a count and a timestamp, not the vectors. The in-memory copy is also dropped after an indexing run that adds or replaces photos.
- With NumPy installed (it arrives with face detection), the vectors are held as one matrix and a search scores all of them in a single step. Without NumPy, the previous one-by-one scoring is used.
- Results are the same as before: the same ranking and the same scores.

### Not changed

- No new setting, no database change, and no change to how meaning search is set up or used.
- The meaning-search model is still loaded again for each search when no loaded model is passed in. This is now the larger share of the time for the first page of a search and is not part of this release.

## Verified

- Test suite: 561 tests, all passing, including two new ones. One asserts that the NumPy and the one-by-one scoring return the same ranking and scores. The other asserts that the in-memory index is reloaded after the embedding table changes.
