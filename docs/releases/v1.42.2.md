# Trash no longer fails while a library scan is running

## Why this release

- Moving a photo to Trash could fail with "Could not move to Trash: FOREIGN KEY constraint failed" when a library scan was running. The scan holds the database for most of its run. A photo's file had already been moved out of the library by the time the move waited for the database, and the scan, finding the file missing, removed the photo's record in the meantime. Recording the move then failed, the file was put back, and the photo was left without a record. Its tags, people and face assignments were removed with the record, and the photo reappeared only as a new, untagged entry after a later scan.

## What changed

### Trash

- **Trash this photo** in the photo viewer, **Trash selected** in the grid, and **Keep best copies** on the duplicates page now take the database first and move the file only after the move is recorded. When a scan is running, the move waits for the scan instead of failing.
- A photo that a scan has already removed from the index is reported as no longer available, and its file is left where it is.
- If moving the file fails, the recorded change is rolled back, as before.

### Library scan

- Before a scan removes the record of a missing photo, it checks the record again. A photo that has since been moved to Trash, or whose file is back in place, is kept, together with its tags and people.

## Verified

- Full test suite: 671 tests, all passing.
- New tests cover the scan keeping a photo that was moved to Trash after being listed as missing, the scan keeping a photo whose file returned, Trash waiting for the database lock before the file moves, and Trash leaving the file in place when the photo's record is already gone.
