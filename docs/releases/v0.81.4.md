## Motivation

When publishing metadata to photos, failures were completely silent. The server log showed only a progress counter (`[Publish] 25/3586 photos`) with no indication of which photos succeeded, failed, or why. The UI showed a cryptic "Published metadata to 3,577 of 3,586 photos" with no way to identify the 9 that failed. This made it impossible to diagnose or fix publishing problems.

## What changed

### Server log — per-photo detail

Every photo now gets its own log entry during publishing:

- **Success**: `[Publish] Wrote: 2023/photo.jpg — R. David Paine III, Kimberly Landry` — shows the file path and the names written.
- **Failed**: `[Publish] Failed: 2023/photo.jpg — The safety backup could not be verified` — shows the file path and the error message.
- **Skipped**: `[Publish] Skipped (not publishable): 2023/video.mp4` — for files that aren't JPEG/HEIC.

A summary line at the end reports how many failed or were skipped.

The same logging was added to the People Review per-person publish path (`publish_person_metadata`), which had the same silent-failure pattern.

### Publish page — failure details in the UI

When any photos fail, the "Published metadata to X of Y photos" message now includes a collapsible "N photos failed" section with a table listing each failed file path and the reason it failed.

### Backend

- `publish_run` now collects failures into a `failed` list (with path and reason) and returns it in the JSON response.
- `_publish_people_metadata` now returns `people` and `relative_path` in its result dict for logging.
- The bare `except Exception: pass` in `publish_run` was replaced with proper error capture.
