Direct follow-up on v0.28.0's "Restart to apply": *"shouldn't you check for the
open terminal window first, kill that window, and then start a new one"* —
followed a beat later by *"or actually the other way around, start a new
window and then kill the old one."* Both instincts were right; the second
one is the safe order.

## The window was never going to close itself

`Start LensLedger.cmd` ends with a bare `pause` (line 60) no matter how the
script exits — normal shutdown, error, or being force-killed. That's
deliberate: it's what lets someone read an error message before the window
disappears. But it means the window a restart is trying to replace never
closes on its own; it just sits at "Press any key to continue . . ." forever,
and `v0.28.0`'s new restart-in-place flow — spawn a fresh copy, wait for the
old process to exit — never touched that window at all. Every restart left
one more of them behind. Manually re-running `Start LensLedger.cmd` while an
old instance was still up had the identical bug, just older: its own
port-5309 cleanup step already force-killed the old *process*, but never
its window either.

## New window first, old window second

The reporter's revised ordering is the correct one for a reason worth
stating plainly: if closing the old window happened first and the new copy
then failed to start for any reason, there would be nothing left running at
all — worse than the clutter this is fixing. `launch_lensledger()` in
`lensledger_updater.py` now starts the replacement, and only after that
succeeds does it close the old one.

## Closing a window is a hard action to get wrong safely

The part that took the most care: identifying *which* window is safe to
close automatically. The candidate PID is whatever `os.getppid()` was for
the process being restarted — for a `Start LensLedger.cmd` launch, that's
exactly the `cmd.exe` running the script. But if LensLedger was started some
other way (directly from an interactive shell, as in development), that
same lookup would return the shell itself — and force-closing someone's own
terminal because they happened to launch LensLedger from it would be a
genuinely bad, surprising thing for the app to do on its own.

So `close_old_launcher_window()` never acts on a PID alone. It queries that
process via `Get-CimInstance Win32_Process` and only proceeds if *both* the
process name is `cmd.exe` *and* its own command line names
`Start LensLedger.cmd` — the exact, specific signature of the disposable
launcher, and nothing else. Anything that doesn't match — a shell, a
different tool, anything — is left alone.

## Verified

- Full automated suite (73 tests, five new) green — covering: the CLI
  dispatch threads `--old-window-pid` through to `launch_lensledger`;
  `close_old_launcher_window` only shells out for a positive PID on
  Windows and is a no-op everywhere else; the PowerShell it builds
  targets the exact PID and names `Start LensLedger.cmd`;
  `launch_lensledger` starts the new copy strictly before closing the old
  one; and closing is skipped entirely when no old-window PID is given.
- The updated PowerShell in `Start LensLedger.cmd` was parse-checked with
  `[System.Management.Automation.Language.Parser]::ParseInput` (syntax
  only, no execution — deliberately, since the real command targets
  whatever's listening on port 5309, which could be a real running
  instance).
- Confirmed nothing was actually listening on port 5309 at the time, then
  ran the exact real command from the script as a live no-op smoke test —
  it completed cleanly with zero side effects, as expected with no matching
  listener.
- Separately verified the core detection mechanism on a disposable,
  harmless test process (a throwaway `cmd.exe` launched with `Start
  LensLedger.cmd` on its command line, unrelated to port 5309 or the real
  app): `Get-CimInstance` correctly reported `Name=cmd.exe` and a matching
  command line, then the test process was cleaned up.
