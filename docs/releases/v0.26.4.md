A question about how updates actually reach people, and one real gap it
surfaced: LensLedger couldn't tell "deliberate git checkout" apart from
"extracted release ZIP, never installed" — and gave the git-only answer to
both.

## Two ways to end up unmanaged, one message

`Check for updates` only works against a *managed* install — the copy
`Install LensLedger.cmd` creates under `%LOCALAPPDATA%\Programs\LensLedger\`,
marked with `.lensledger-managed.json`. Anything else reports as
unmanaged and refuses to self-update, correctly. But "unmanaged" covers
two very different people:

- Someone who deliberately cloned the repo to run from source — knows
  exactly what they're doing, `git pull` is the right answer.
- Someone who downloaded the release ZIP, extracted it, and double-clicked
  **Start LensLedger.cmd** instead of **Install LensLedger.cmd** — the app
  works fine, but silently can never update itself again, with no signal
  that they skipped a step.

The update panel used to give both the same message: *"This is a source
checkout... update it with git pull, or run Install LensLedger.cmd once."*
Correct for the first person, confusing for the second — there's no `git`
anywhere in their setup.

## The fix

`/api/update/status` now reports whether the current folder is a `.git`
checkout. The update panel uses that to give each case its own message:
the git-checkout wording stays as-is, and the extracted-copy case now
says plainly — *"This copy was run directly from an extracted download...
Run Install LensLedger.cmd once from this same folder to move LensLedger
into a managed copy that updates itself automatically from then on —
your photo library and catalog are unaffected."*

Also added the same heads-up directly to `Start LensLedger.cmd`, printed
before the browser opens, for anyone who'd never think to open the
update menu in the first place.

## Verified

- Full automated suite (64 tests) green.
- Confirmed live against the real, currently-running unmanaged checkout:
  `/api/update/status` correctly reports `managed_install: false` before
  this fix's restart, and the new `is_source_checkout` field is present
  only after picking up the change — confirming the detection logic
  activates exactly when expected, not before.
