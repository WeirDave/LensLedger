Same-session follow-up to v0.30.0: *"dude you built it in the space of the
card so you can't see anything?"* — with a screenshot showing the picker's
search box appearing, and nothing else. The button worked; the dropdown
below it was invisible.

## Verified by DOM state, broken in the actual render

v0.30.0's testing checked things like "does the popover have the `.open`
class" and "does the item list contain the right names" — all of which
passed, because the DOM state genuinely was correct. What that testing
never did was look at the rendered result. The popover was
`position:absolute`, nested inside `.face-card`, which has
`overflow:hidden` (needed elsewhere, for the photo thumbnail's rounded
corners). The instant the dropdown's content extended past the card's own
box, `overflow:hidden` clipped it to nothing — invisible, even though every
element existed, was `.open`, and had the right text.

## Escaping the ancestor, not fighting it

The fix follows the same principle as everything else in this stretch of
releases: stop relying on a container's cooperation and own the whole
mechanism directly. `web/js/person-picker.js`'s dropdown now builds itself
fresh on every open, appended straight to `document.body` — not nested
inside the trigger's card at all — and positions itself with
`getBoundingClientRect()` against the trigger's real screen coordinates,
repositioning on scroll and resize while open. Being a sibling of the card
rather than a descendant, no card's `overflow:hidden` can reach it,
structurally, regardless of any CSS specifics. It's removed from the DOM
entirely on close, so there's nothing to leak across a long session either.

## A gap in how this got verified, and a new standing rule

The user's response to this bug was direct feedback, not just a bug report:
CSS/layout changes need an actual look at the rendered page before they
ship, not DOM-state assertions standing in for a screenshot. That's now
recorded as standing guidance for this repo going forward.

In the interest of being straight about it rather than glossing over the
gap: this specific release could not be verified with an actual screenshot
either — the browser tool's screenshot capability was failing in this
session for reasons unrelated to the code change itself (confirmed via
repeated timeouts across a fresh tab, a window resize, and a tab reselect,
all with the same "browser pane is not displayed" error). What *was*
verified, as the strongest substitute available: the popover element's
`parentElement === document.body` (confirming it's structurally outside
the card's DOM subtree, which is what actually matters — `overflow:hidden`
cannot clip a box that isn't nested inside it, independent of any specific
pixel measurement), `position: fixed` computed style, a bounding rect
entirely within the viewport's bounds, all three dropdown items rendering
at non-zero size, and a full functional round-trip (open → filter → choose
→ confirmed in the database → popover removed from the DOM with zero
leaked afterward). That's real evidence the specific clipping bug is fixed
structurally. It is not the same thing as looking at it, and the user
should confirm with their own eyes that it renders as expected.
