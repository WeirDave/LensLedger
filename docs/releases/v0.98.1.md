## Meaning search install detection fix

After clicking "Set up meaning search" on the Settings page, the install could appear to do nothing — the button would disappear but no progress bar, toast, or model list would appear.

### Root cause

The `is_available()` function in `semantic_index.py` used `@lru_cache` to avoid re-importing `open_clip` and `torch` on every status check. However, `lru_cache` caches the result permanently for the lifetime of the Python process. If the function was first called before the packages were installed (returning `False`), it would continue returning `False` even after a successful `pip install` — the cache was never invalidated.

This caused several symptoms:
- The `/api/semantic/status` endpoint kept reporting `installed: false` after a successful install
- The model list only appeared because of a secondary `install.state === 'complete'` check in the JavaScript
- If the user navigated away and returned, the stale cache caused the setup button to reappear
- If packages were pre-installed from a prior session, clicking the install button triggered a server error ("Meaning search is already installed") that the JavaScript silently ignored

### Fix

Replaced `@lru_cache` with a manual cache that:
- Sticks permanently once `True` (packages don't un-install themselves)
- Can be explicitly cleared via `clear_available_cache()` after a successful pip install
- Re-checks on the next call after being cleared

The `install_semantic_requirements` worker now calls `semantic_clear_cache()` after a successful pip install, so the next status check correctly detects the packages.

Also fixed the JavaScript install button handler to check the server response for errors and show them as a toast, instead of silently proceeding to poll.

## Verified

- Test suite: 101 tests passed
- Cache invalidation logic verified: `is_available()` returns `False` before install, cache cleared after install, returns `True` on next check
- Error response from server now correctly shown as toast in the UI
