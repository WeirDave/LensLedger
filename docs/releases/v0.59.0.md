## Database lives with the library

Previously, LensLedger stored databases in `%LOCALAPPDATA%\LensLedger\Libraries\` by default, separate from the photos. This made it impossible to move a photo library to another drive and have the index come along.

### New default: `.LensLedger` folder inside the library

Databases now default to a hidden `.LensLedger` folder inside each library root:

```
C:\Dropbox\Photos\
└── .LensLedger\
    └── LensLedger-Photos.sqlite3
```

The naming convention is `LensLedger-{folder name}.sqlite3` — branded and self-describing, so a displaced file immediately identifies what it belongs to and what product created it.

### Backward compatibility

Existing libraries with databases in AppData continue to work. The `db_mappings` in `library-state.json` now stores full absolute paths (previously stored just the filename relative to the AppData Libraries folder). Both old-style relative names and new-style absolute paths are resolved correctly.

### "How libraries work" documentation

Added a foundational explanation to the User Manual, Quick guide, and onboarding page:

- A library = one root folder. Everything inside it (all subfolders, any depth) belongs to that library.
- Each library has its own separate database — there is no shared master database.
- Add subfolders, reorganize within the root — the next scan picks up changes automatically.
- Files outside the root folder are not tracked.

### Other changes

- Flipped the default in the onboarding dropdown, add-library prompt, and both server-side handlers from "appdata" to "library".
- Updated hint text to explain the `.LensLedger` folder convention.
- Legacy `library_db_path_appdata()` function preserved for the "application data folder" option.

## Verified

- Test suite: 79 tests passed (two tests updated for the new convention).
- Verified the existing `C:\Dropbox\Photos` library (50,264 assets) loads correctly from the new `.LensLedger` location.
