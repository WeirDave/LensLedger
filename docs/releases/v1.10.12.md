## Why this release

"Write all tags" could list photos under "photos could not be written" for
four separate reasons:

- `No matching files` — for photos whose file name contains a character
  outside the Windows code page, such as U+F03A, which some file-copying and
  renaming tools put in place of a colon.
- `Error reading OtherImageStart data in IFD0` (or `IFD1`) — for photos
  whose EXIF block points at an embedded image that is not actually in the
  file. Some phones save photos this way.
- `JPEG EOI marker not found` — for JPEGs whose image data stops without an
  end marker and is followed by a maker trailer. Some phone panoramas are
  saved this way.
- `cannot identify image file` — for HEIC photos, on installations made
  before HEIC support was added.

## What changed

### Writing tags ("Write all tags", "Publish all", single-photo writes)

- **File names with characters outside the Windows code page are written.**
  ExifTool reads its command line in the Windows ANSI code page. Any other
  character arrived as `?`, which ExifTool then treated as a wildcard, and
  the write failed with "No matching files". Every ExifTool call now passes
  its arguments through a temporary UTF-8 argument file, so the file name
  arrives unchanged.
- **Tag text is written exactly.** The same code-page problem applied to the
  values being written. A keyword, person's name, title or description
  containing characters outside the code page (for example "ā" or "日本") was
  stored with those characters replaced, usually by `?`. These values are
  now written exactly as LensLedger holds them. Line breaks in a title or
  description are preserved.
- **Photos with a broken EXIF image pointer are written.** ExifTool cannot
  rebuild an EXIF block that points past the end of the file, so any write
  that touches EXIF was refused. When this happens, the write is repeated
  without the EXIF description field. Keywords, people, title and
  description are written to XMP and IPTC, which are separate parts of the
  file, and the EXIF block is left exactly as it was.
- **JPEGs with no end marker get a sidecar file.** ExifTool will not rewrite
  these files without changing the image data. When "Write mode" (Settings →
  Metadata publishing) is "Embedded (modify photo files)", "Write all tags" now writes a sidecar `.xmp` file
  next to the photo instead. The photo is listed under "got a sidecar file
  instead" with the reason, and the photo itself is not changed. The next run
  tries the embedded write again, so the photo stays listed until it can be
  written. Writing tags to a single photo in that mode reports the
  same reason as an error.

### Starting LensLedger ("Start LensLedger.cmd")

- **Missing required packages are installed on any launch.** The launcher
  previously installed the Python packages only when Pillow was missing,
  that is, on first launch. An installation made before `pillow-heif` joined
  the requirements never received it, so HEIC photos could not be opened for
  writing, face scanning or meaning search. The launcher now checks for
  every required package and runs the install when any one is missing.
  Existing installations pick up `pillow-heif` on their next start.

The safeguards on every embedded write are unchanged: a verified safety copy
is taken first, the picture pixels are compared afterwards, and the photo is
restored from the safety copy if anything fails.

## Verified

- Full test suite: 237 tests, all passing.
- Three new regression tests, each confirmed to fail without the fix:
  - A photo whose name contains U+F03A, tagged with a keyword containing
    "ë", "ā" and "日本" and a title containing a line break, a backslash, `$`
    and `@`. The write succeeds and every value reads back exactly.
  - A synthetic photo whose IFD0 image pointer lies past the end of the file.
    The write succeeds, the description and keywords are in XMP and IPTC, and
    the pixels are identical.
  - A synthetic JPEG with no end marker followed by a maker trailer. The run
    reports it under "got a sidecar file instead", the sidecar carries the
    tags, the photo's bytes are unchanged, and a second run reports it again.
- A scratch copy of a photo with a broken IFD0 pointer, outside the library,
  was written with the fix. The tags landed and the pixels were identical.
- ExifTool's handling of the argument file was checked directly: values with
  line breaks, tabs, backslashes, quotes, `$`, `@` and non-Latin characters
  round-trip exactly, and a single leading space is kept.
