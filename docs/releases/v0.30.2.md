Started as a routine dead-code removal and turned up a real bug along
the way.

## A modal nobody could open

While auditing `web/js/viewer.js` for unreachable code, one cluster stood
out: a full embedded "people review" modal — `openPeopleReview`,
`buildPeopleReview`, `renderPeopleReview`, `submitPeopleReview`,
`undoPeopleReview`, plus its own tracking state — wired into the
hamburger menu's dispatcher under the key `review-people`. Grepping the
whole repo for that key, and for the modal's own DOM ids, turned up
nothing: no template anywhere ever set `data-panel="review-people"`. The
real "Review people" buttons — the hamburger menu entry and the people
gallery's own button — both link straight to the standalone
`/people-review` page instead, bypassing the modal path entirely. It was
confirmed dead in a live browser session before anything was removed:
the button's click handler navigates by `location.href`, never touching
`openMenuPanel('review-people')`.

Removed the whole cluster, plus the CSS rules that only that modal used
(`.people-review-modal`, `.review-progress`, `.review-main`, and the
rest of that block in `web/css/viewer.css`) — checked first against
`people-review.css`, the standalone page's own stylesheet, to make sure
none of those class names were secretly shared; they aren't, the
standalone page uses entirely different names (`.review-card`,
`.review-head`, etc.).

## The rest of the sweep

Same rigor, applied to the rest of `viewer.js`/`viewer.css`: every
`data-panel`/`data-help` dispatch key checked against what
`src/photo_search.py` actually emits, every element id checked against
the templates, every top-level function checked for a live call site,
every CSS class checked against both JS and the HTML templates. Found
and removed:

- `openLibraryPanel()` — fully superseded by `openLibraryPanelV2()`; the
  menu only ever calls the V2 version.
- `esc()` — an HTML-escaping helper with zero call sites.
- A diagnostics-panel CSS block (`.diagnostics-panel`, `.health-summary`,
  `.health-paths`, `.job-card`, `.job-actions`) left behind in
  `viewer.css` from before the scan/diagnostics UI moved to its own
  `/scan-photos` page — that page loads its own `scan-photos.css`, which
  defines the same classes independently, so `viewer.css`'s copies were
  pure dead weight.
- `.editor-guide`, `.section-description`, `.hint`, `.metadata-grid`
  (+ `.wide`), `.metadata-actions`, `.pager` — all superseded by other,
  currently-live class schemes elsewhere in the same file.

The other six page bundles (`map`, `onboarding`, `people-review`,
`faces-review`, `scan-photos`, `person-picker`) came back clean.

## The worktree bug

Running the full suite against this worktree turned up two failures
that had nothing to do with the cleanup — `is_source_checkout` reporting
`false`, and `POST /api/update/restart-source` returning 400 — both
reproducible on the unmodified tree too. The cause: `.git` in a git
worktree is a plain text file (`gitdir: <path to the real .git>`), not a
directory, but `update_status()` and `restart_source()` in
`src/photo_search.py` both checked `(install_root / ".git").is_dir()`.
`src/lensledger_updater.py` already handles this correctly elsewhere
with `.exists()`, which accepts either shape — both checks in
`photo_search.py` now match that pattern, so restart-in-place works
correctly whether LensLedger is running from a plain clone or a
worktree checkout.

## Verified

- Full automated suite: 74 tests, all green (two pre-existing, unrelated
  failures on this worktree — `is_source_checkout`/`restart_ready` — are
  what led to the `.git` detection fix above; confirmed present on the
  unmodified tree via `git stash` before attributing them, and gone
  after the fix).
- Live browser session against a real scanned library: main viewer
  loaded with no console errors, all network requests for
  `viewer.css`/`viewer.js` returned 200, the hamburger menu opened, and
  "Open photo library" opened the (still-live) `openLibraryPanelV2`
  modal correctly. Separately loaded `/scan-photos` and confirmed its
  diagnostics UI still renders correctly from its own stylesheet,
  unaffected by the `viewer.css` cleanup.
