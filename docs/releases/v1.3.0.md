## Why this release

"Write all tags" on the Publish photos page offered to write "auto-classified
tags, people, OCR text" into photos. In the default write mode — embedded,
meaning the tags go inside the photo file itself — it wrote only the names of
people. Auto-classified tags and text found in pictures were assembled and then
discarded, with nothing on screen to say so. Choosing the sidecar mode instead,
which writes a small companion file next to each photo, did write all three.

The capability was never missing. Publishing a single photo from its own page
already wrote everything. The bulk button was simply wired to the wrong path.

This release wires it to the right one, and makes the page say what a given file
could not take rather than quietly writing less than promised. It also adds the
two re-scan controls that were missing: a way to fill in photos with no meaning
data, and a way to scan photos that have already been scanned.

## Write tags to photos

"Write all tags" now writes, into the photo file itself:

- every tag on the photo, including the auto-classified ones
- the names of everyone confirmed in People
- the photo's subject, as Title and Headline
- any text found in the picture, as the Description and Caption

Anything that could not be written is now listed by name underneath the button,
with the reason. Two cases produce a line there:

- **A file that cannot carry embedded tags at all** — a PNG, for instance. It
  gets a sidecar file next to it instead, and is named as having done so. The
  substitution used to happen silently.
- **A file that could not take a particular field.** The photo is read back
  after writing and each category is checked, so a format that accepts tags but
  not a description says exactly that.

A file that simply has nothing in a category — no subject set, no text in the
picture — is not reported. Nothing was promised for it.

### It no longer freezes the page

Writing tags across a library used to run inside the button press, so the page
sat still until every photo was done. It now runs in the background with a
progress bar, and a **"Stop writing"** button beside "Write all tags" stops it
between photos. Reloading the page while a run is in progress picks the progress
display back up.

### Two smaller corrections

Tags made only of punctuation are no longer written into photos. A photo sitting
directly in the top level of a library could pick up a tag of "." from its
folder, which then went into the file as a keyword.

The write is now a single metadata operation rather than a clear pass followed by
a write pass. The old two-step left a window in which an interrupted write could
leave a photo stripped of its old keywords and not yet carrying the new ones.

## Re-scanning and filling gaps

### Meaning search

Two buttons are new on the **Scan your photos** page, in the "Meaning search"
section, beside the existing "Build / resume meaning index":

- **"Fill in missing"** — indexes every photo that has no meaning data,
  including photos an earlier run could not read. This matters because a photo
  that failed once was recorded as failed and then skipped by every later run,
  permanently. Nothing retried it. "Fill in missing" clears that record and
  tries again.
- **"Re-scan everything"** — reads every photo again from scratch, including
  photos already indexed. It asks for confirmation first, because on a large
  library it is a long job.

The same section now shows a **"Missing"** count: photos with no meaning data at
all. Clicking it lists them.

### Text recognition

The "Local text recognition (OCR)" section has a new checkbox, **"Read photos
again that have already been read"**, unticked by default. Ticked, the next run
re-reads photos that were already processed instead of only picking up new ones.
It asks for confirmation first.

### Naming files rather than counting them

A scan that cannot read a photo now shows the file name and the reason on the
page while the scan is still running, under the progress figures. Previously a
failure only moved a counter, and the names were available only after the run
finished.

## Fixed during testing

**The setup links never went away.** "Set up meaning search in Settings" and
"Set up face detection in Settings" stayed on screen after those features were
already installed, sitting next to the buttons that only appear once they are.
The rows were being marked hidden, but a layout rule was overriding that. This
predates the release; it became obvious once the meaning search row had more
buttons in it.

**A checkbox detached from its label.** The new OCR re-read checkbox inherited a
width meant for date and number fields, which pushed it a long way from its own
text.

## Verified

- Full test suite: 125 tests, all passing, on Python 3.12.10.
- Four new tests cover writing tags into the photo file, matching the coverage
  the sidecar route already had. One asserts each category separately, so if any
  one of tags, people, description or subject stops being written the failure
  names the missing category. This was confirmed by deliberately disabling the
  description write and checking the test failed and named "description".
- Further new tests cover the safety copy matching the original bytes, the
  picture pixels being unchanged by a write, a file that cannot be embedded
  being reported by name, the three meaning-search modes, a failed photo being
  skipped by an ordinary run but picked up by "Fill in missing", the stale
  failure record being cleared, failures carrying a file name and a reason, the
  "Missing" count, and the OCR re-read selecting photos already read.
- Checked in a browser against a library of generated test images: the meaning
  search "Fill in missing" and "Re-scan everything" buttons, the OCR re-read
  checkbox, the write-tags progress and per-file report, and the failure list
  shown during a scan. Verified in both light and dark themes.
- Confirmed by reading the files back afterwards that auto-classified tags and
  recognised text now appear in the written photos, and that a PNG received a
  sidecar file and was named on the page as having done so.
