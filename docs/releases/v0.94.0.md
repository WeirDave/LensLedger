LensLedger has had a good self-updater for a while, but only for one kind of install. A **managed installation** — the copy `Install LensLedger.cmd` creates under `%LOCALAPPDATA%\Programs\LensLedger` — could check GitHub, download a verified release, swap the tree, and restart itself. Everything else was a dead end.

If you installed by cloning the repository, the update panel checked for updates, found one, and then told you:

> This is a source checkout, so it can't update itself automatically.
> Update it with git pull, or run Install LensLedger.cmd once to create a separate managed copy.

That is a strange thing for an app to say. The one install shape that can update *most* cheaply — fetch a few kilobytes of objects, move HEAD — was the only one that made you drop to a terminal.

## What changed

A source checkout now updates itself from the same panel, using git instead of a download.

Press **Install update** and LensLedger fetches from GitHub, checks out the newest release tag in place, and restarts into it. There is no ZIP, no staging directory, and no tree swap — the work is a fetch and a checkout, so it finishes in about a second on a normal connection.

The managed-install path is completely untouched. It still downloads the verified release asset, checks its digest, stages, validates the tree, installs, and hands off to the updater helper. The two mechanisms cannot collide: `FORBIDDEN_ROOT_NAMES` already refuses to let a ZIP install write over a `.git` directory.

## What it refuses to do

Updating a checkout means checking a release tag out over whatever is in the folder, so the update stops before touching anything when either of these is true:

- **The checkout has local work** — commits you haven't pushed, or tracked files you've edited. The panel says so and does nothing. This is what stops a development copy from having a release tag checked out over work in progress.
- **Tracked files are modified.** The specific files are named in the message so you can revert or move them.

Files you added yourself — notes, scratch images, anything untracked — are never touched, because a checkout only writes paths the release actually ships.

There is also a quieter safeguard: if the newest release tag is the version you already have, the update returns without checking anything out. Skipping that would detach HEAD from your branch to land on the commit it already points at, which changes nothing but looks alarming in a healthy clone.

## How a working copy is recognized

Deliberately *not* by looking for `tests/` or `.github/`. Someone who installs by cloning gets those directories too, so a file-marker test would have blocked the update for every git user — the exact bug this release is meant to remove.

The signal is git state. Installing leaves HEAD detached at a release tag, so a detached HEAD is always an ordinary install. An attached branch only counts as a working copy when there is something to lose: unpushed commits, or modified tracked files.

## Verified

- Full suite: **101 tests, all passing** (up from 88).
- New `GitUpdateTests` build a real bare origin, a real clone, and real tags in a temp directory rather than mocking git — covering the update itself, the already-current no-op, version-ordered tag selection (`v0.9.10` beats `v0.9.9`), refusal on edited tracked files, refusal on unpushed commits, untracked files surviving, and a non-checkout directory being rejected.
- New server tests cover the git branch of `/api/update/install`: a successful update reporting `restarting`, an already-current result that does *not* spawn a restart, a git refusal surfacing to the user as a 400, and a missing git binary being reported plainly.
- The existing test asserting a source checkout was refused has been rewritten — that behavior is what this release removes. An extracted, non-git copy is still correctly refused.
