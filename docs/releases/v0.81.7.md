## What happened

When a person was identified from the photo viewer (the "Who is this?" flow on the search/viewer page), the `add_person` method inserted an `asset_people` row without setting the `face_id` column. The faces-review page excludes already-identified faces by matching `asset_people.face_id = face_embeddings.id` — but since `face_id` was NULL, the SQL `NULL = id` comparison always returned false, and the face kept appearing as unidentified.

Worse, if a face had been correctly confirmed via the faces-review page (which does set `face_id`), and the same person was later re-confirmed from the photo viewer, the ON CONFLICT UPDATE clause would overwrite the existing `face_id` with NULL — causing a previously resolved face to resurface.

## What changed

The `add_person` method now resolves the largest unlinked face embedding on the photo and sets it as `face_id` in the `asset_people` row. The ON CONFLICT UPDATE uses `COALESCE(excluded.face_id, asset_people.face_id)` so re-confirming from the viewer never clears an existing `face_id`.

Additionally, two unidentified-face count queries (search page sidebar and scan-photos stats API) were missing the `f.unknown_at IS NULL` filter that the faces-review page itself uses. Faces marked as "unknown person" were inflating the count shown in the UI but didn't actually appear on the review page. Both queries now match the canonical filter.
