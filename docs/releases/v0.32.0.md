Four pieces of direct feedback from live use of the Name-faces page while a
background face scan was running: a confusing "catalog is busy" dead end,
no way to open the full photo for context, no way to dismiss a real-but-
unidentifiable face, and a batch "Confirm all" that looked broken when it
wasn't.

## The busy message lied about what happened

`do_POST`'s catch-all for `sqlite3.OperationalError` (`src/photo_search.py`)
returns 409 with a fixed string whenever a write collides with another
connection's lock — but the string hardcoded "No names were merged," a
holdover from when `/api/person/merge` was the only route that could hit
it. Every other route sharing that same catch block — naming a face,
marking one "not a person," anything — showed that same merge-specific
sentence regardless of what had actually failed. The message is now
route-agnostic and explains the actual cause (a scan or other change using
the catalog right now), and the response carries a `"busy": true` flag so
the frontend can tell a transient lock conflict apart from a real error
without string-matching the message text.

That flag feeds a new `apiRetry()` in `faces-review.js`: every write on
this page (`name`, `ignore`, `unknown`) now retries once automatically
after a few seconds on a busy response, showing "A scan is using the
catalog right now — retrying in a few seconds…" while it waits, rather
than leaving the user staring at a bare error with no explanation of what
to do next. (The server already blocks a single write for up to 30s via
`SQLITE_BUSY_TIMEOUT_MS` before this even fires, so most contention windows
are much shorter than that — a scan's own commits happen in bursts, not as
one continuous lock — which is why a short client-side retry has a real
chance of landing in the next gap.)

## Click-to-enlarge and "Unknown person"

Both are direct ports of mechanisms People review already shipped in
0.31.0, reused rather than reinvented:

- **Lightbox** — `markFace()`'s letterboxed box-drawing geometry from
  `people-review.js` is unchanged, just fed faces-review's own data shape.
  That required a real backend change first: `/api/faces/unidentified`
  never returned `box_left/top/right/bottom` even though the SQL `WHERE`
  clause already guarantees every row has them (the crop endpoint uses
  them server-side but the JSON response dropped them) — added them so
  the lightbox has something to draw.
- **Unknown person** — a new `/api/faces/unknown` endpoint
  (`mark_face_unknown`) mirrors `ignore_face()` exactly, but stamps
  `unknown_at` instead of `ignored_at` — the same column People review's
  "Unknown person" disposition already writes
  (`FACE_DISPOSITION_COLUMNS`), so both routes into that state stay
  equivalent for `face_learning.learn()`'s suggestion filtering. Also
  added `unknown_at IS NULL` to `/api/faces/unidentified` and
  `_find_similar_unidentified_faces()`'s `WHERE` clauses, which only
  checked `ignored_at` before — without that, a face marked "unknown"
  would keep resurfacing in the queue and as a match suggestion for
  someone else, defeating the point of marking it.

## Confirm-all's silent-then-wrong-error bug

The reported symptom: clicking "Confirm all" on 3 photos showed a static
"Confirming…", then flipped to a busy error — but 2 of the 3 had actually
gone through moments later. Reading the old loop explained why: it
`await`ed each item sequentially, applied successes to the UI immediately
and silently, kept looping after a failure instead of stopping, and only
ever displayed the *last* error seen — so a mid-batch failure's message
could sit on screen while a later item quietly succeeded underneath it,
and there was never an accurate count of what actually happened.

Rewrote the loop to track successes and failures separately, show real
per-item progress ("Confirming 2 of 3…"), route every attempt through the
new `apiRetry()` so a transient busy failure self-heals before counting
as a real failure, and end with an honest summary. A genuine failure
leaves its thumbnail outlined red with the error as its tooltip and keeps
the group open with re-enabled buttons — clicking "Confirm all" again
retries only what's still checked, since successful items already removed
themselves.

## Verified

- Full automated suite: 79 tests (77 prior + 2 new: `/api/faces/unknown`
  marks the right column and disappears from the queue, and the busy
  message reads generically on a non-merge route), all green
  (`PYTHONPATH=src python -m unittest discover -s tests`).
- Live-tested against a real scratch library/DB via a second server
  instance (kept fully separate from the live library mid-scan): confirmed
  the lightbox opens on double-click with `/media?id=...` and a drawn face
  box, "Unknown person" removes the card and stamps `unknown_at`, and —
  by temporarily monkey-patching `fetch` in the page to simulate a 409
  then a real backend response — confirmed `apiRetry()` retries exactly
  once with the expected status message, and confirmed the "Confirm all"
  rewrite reports "1 confirmed, 1 failed" with the failed thumbnail
  outlined and the group left open, matching a simulated mixed-result
  batch.
- Could not capture pixel screenshots in this session (the browser pane
  rendered at a 0px-height viewport throughout), so verification here was
  functional (DOM state, network calls, computed values) rather than
  visual — worth a look at the real page next time you're on it.
