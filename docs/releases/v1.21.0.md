## Why this release

1.20.0 let LensLedger put its star ratings into your photo files. The other
direction was missing: a rating you gave a photo in Lightroom, or any other
program, never showed up here. The two catalogs could only drift apart.

That is not as simple as importing. Since 1.20.0, clearing a rating here
deliberately leaves the file's rating alone. A scan that simply read the file
would bring every rating you had cleared straight back.

## What changed

**Scanning reads ratings**

- A rating already in a JPEG, HEIC, PNG, WebP or TIFF file is imported for any
  photo you have not rated here. These are the same file types LensLedger
  already reads tags from, and the rating is read the same way, directly from
  the file, with no extra process per photo.
- It reads both ways the XMP standard allows a rating to be written, as an
  attribute (what Lightroom writes) and as an element (what LensLedger writes),
  under whatever prefix the file uses.
- Your first scan after updating re-reads every photo once, so ratings already
  in your files come in. It reads only the start of each file, with no
  decoding, so it is quick.

**When the file and LensLedger disagree**

LensLedger now remembers the rating each file held the last time it read or
wrote it. The one that has changed since then wins:

- Only the file changed (you re-rated in Lightroom): the file's rating replaces
  yours here.
- Only LensLedger changed: yours stays, and the next **Write all tags** puts
  it in the file.
- Both changed: yours wins.
- Neither changed: nothing happens.

**Clearing, and ratings that vanish**

- A rating you clear here stays cleared, even though the file still holds it.
  The file still holds what LensLedger last saw, so it is not a change.
- A rating that disappears from a file never clears yours. A program that
  strips metadata would otherwise unrate a library. The rating is put back in
  the file by the next **Write all tags**.

**Write all tags checks first**

Before writing a photo, **Write all tags** now settles its rating against the
file. Without that, a rating you changed in Lightroom since the last scan would
be overwritten with the older one held here. After a rating is written, it is
recorded as what the file holds, so clearing it here afterwards stays cleared.

**Not read**

- Lightroom's rejected flag (-1) is ignored; LensLedger has no such state.
- Windows' own percentage rating (`MicrosoftPhoto:Rating`) is a different field
  and is ignored. Only values 1 to 5 count.
- RAW and video files, and ratings in separate `.xmp` sidecar files, are not
  read. That is a separate change, because a sidecar can belong to another
  program.
- A file that cannot be read is skipped, not treated as unrated.

## Database

Schema version 25 adds an `asset_rating_sync` table, keyed by the photo's path
like ratings, holding the rating each file had when it was last read or
written. It is created automatically on first start; older versions ignore it.

## Fixed during testing

- **A rename could replace a rating you set.** A renamed photo is scanned as a
  new photo first, which now reads its rating from the file. The rename step
  then moves the old records across, but it silently skipped any that already
  existed at the new path. A photo you rated 5 here, with 4 in its file, came
  out of a rename rated 4. The records from the old path now replace the new
  path's, and the two are settled against the file again.
- A test of the 1.20.0 rule "an unrated photo leaves the file's rating alone"
  failed, correctly: scanning now imports the rating the file already holds, so
  the photo is no longer unrated. The test now clears the rating here first,
  which is the case the rule still covers.
- Two checks passed even with the rule they test removed. The test for
  Windows' percentage rating used a value outside 1 to 5 that would have been
  ignored anyway, and no test covered a library upgraded from 1.20.0, which
  has ratings but no record yet of what the files held. Both are covered now.

## Verified

- Full test suite on Linux with the official command: 344 tests, 339 passing or
  skipped. The 5 that fail are the same five that run the bundled Windows
  `ExifTool.exe`, as in 1.20.0. The Windows CI run is the authority for those.
- The same suite on Linux with a system ExifTool 12.76 in place of the bundled
  one: 344 passing, including those five.
- 23 new tests: reading a rating in each written form and ignoring values
  outside 1 to 5, the Windows rating, and unreadable or unsupported files; all
  twelve cases of the merge rule; importing on scan; leaving a rating set here
  alone; both sides changed; a rating changed elsewhere; a rating cleared here;
  a rating removed from the file; the one-time re-read on upgrade; ratings and
  their records following a renamed photo, including a library upgraded from
  1.20.0; **Write all tags** taking a rating changed elsewhere, and keeping
  one set here; and a written rating being remembered.
- Each rule was checked to fail with it removed: 13 changes in all, covering
  the merge rule's cases, the rename handling, the one-time re-read, the
  reader's range and namespace checks, treating an unreadable file as unrated,
  settling before a write, and remembering a written rating. Two survived on
  the first run because of the test gaps above and were fixed.
- The manual served by the running app, in Chromium against a generated test
  library: the Star ratings section shows the new explanation as a list.
- **Limit of the checking:** the test photos are generated JPEGs with
  hand-built XMP that follows the standard. They were not checked against files
  Lightroom wrote, because real photos cannot be committed. A program that
  writes its rating some other way will simply have no rating imported.
