## Why this release

The test for building and searching the meaning index failed on macOS and
Linux but passed on Windows. It scanned three photos and then asserted that
`beach.jpg` was photo number 1 and `document.jpg` was photo number 2. The scan
numbers photos in the order the operating system lists the folder. Windows
lists files alphabetically, so the guess held there; Linux and macOS return
them in no fixed order, so the numbers came out differently.

The program was never wrong. A photo's number is only an internal key, and
nothing depends on which photo gets which number. Only the test assumed it.

## What changed

- The test now looks up each photo's number by file name and checks the
  search results against that, so it no longer depends on listing order.
- No program code changed.

I considered sorting the scan instead, which would have made the numbering
repeatable. I did not: the scan streams through a library so it can show
progress and be cancelled, and sorting would make it list every file before
starting, which costs time and memory on a large library for no benefit to
anyone.

## Fixed during testing

The first version of this change looked the numbers up with
`with sqlite3.connect(...) as con:`. That form commits the transaction but does
not close the connection, so the database file stayed open. Linux allows
deleting an open file, so it passed there. On Windows the test's temporary
folder could not be removed (`WinError 32`), and the Python 3.14 job on the
pull request failed. The connection is now closed explicitly.

## Verified

- Full test suite on Linux: 311 tests, 306 passing or skipped. The 5 that
  fail are the same five that need the bundled Windows `ExifTool.exe` and
  cannot run off Windows. The meaning-search test, which failed on Linux
  before, now passes, and it passed on four repeated runs. The Windows CI
  run is the authority for the rest.
