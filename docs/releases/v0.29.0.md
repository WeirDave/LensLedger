A pass through direct feedback on the two pages from the last couple of
releases: Name faces (v0.27.0/v0.28.0) and the main viewer's date filter,
all reported the same day.

## The date field is no longer the browser's problem

The report that started this: the toolbar's `<input type="date">` opens a
totally different picker in every browser — Firefox's buries year
navigation behind clicking the month label in its popup, and the reporter's
exact complaint was pointed: *"there are 4 main browsers and I loathe making
different experiences for each."*

That's a fair objection to relying on a native form control at all. The
field is now a plain button (`#dateTrigger`) that opens a calendar panel
LensLedger builds and owns — Month and Year `<select>` dropdowns (Year goes
back to 1900), prev/next month arrows, a day grid, and Today/Clear. None of
it delegates to browser-native picker UI, so it looks and behaves *exactly*
the same in Chrome, Firefox, Safari, and Edge — there's nothing left for a
browser to render differently.

Under the hood, `#datePicker` stays a real `<input type="hidden" name="date">`
so the existing `changeDay()` day-step buttons and the scope-picker's
clear-the-date-on-people-search logic (`web/js/viewer.js`) needed no changes
at all — they already only cared about a form field named `date` with a
`YYYY-MM-DD` value, which the new widget still provides.

## Two bugs on Name faces, reported with screenshots

**The address-autofill popup.** Clicking into "Who is this?" sometimes
opened the browser's own saved-address suggestions instead of (or under)
the list of known people — Firefox in the reporter's case, matched against
their real saved address. None of the app's name-entry fields — Name
faces' "Who is this?", People review's "Correct name", the main viewer's
"Person's name" — had ever set `autocomplete`, so the browser was free to
guess. All three now set `autocomplete="off"`.

**The vanishing Save button.** Screenshots showed every face card missing
its Save button entirely, with "Who is this?" stretched to the card's full
width. Measuring the actual boxes in a live browser session pinned it down:
`.face-info` is `display:grid` with an implicit column, and that column was
sizing itself to its widest child's *natural* width (input + button
un-shrunk, 233px) rather than the card's real width (192px) — and because
`.face-card` has `overflow:hidden`, the 41px difference was silently
clipped instead of visibly overflowing. `grid-template-columns:minmax(0,1fr)`
on `.face-info` lets that column shrink to fit like it should have from the
start.

## Also

- Name faces' per-card caption now shows the filename first instead of
  date + folder, since several faces from one photo burst share both and
  the caption previously truncated the filename away entirely. Full detail
  (date, folder, filename) is still there as a hover tooltip.

## Verified

- Full automated suite (69 tests, one new — asserting the date field
  renders as a hidden input plus trigger button, not a native date input,
  and that the calendar's JS functions are present in the served script)
  green.
- Manually verified live in a browser: opened the calendar, jumped directly
  to 2019 via the Year dropdown, selected March, clicked day 15, confirmed
  the form submitted and the photo list correctly filtered to the one
  matching photo with the trigger button reading "Mar 15, 2019"; reopened
  the calendar and confirmed it showed March 2019 (not today) since that's
  the active selection; clicked Clear and confirmed it reset to "Any date"
  and both seeded photos reappeared; checked popover positioning stayed
  on-screen at both a ~900px and a narrower (~800px effective) viewport.
  Separately confirmed the Name faces Save-button fix by measuring actual
  card/button box widths before and after the CSS change, and confirmed
  the new caption format (filename first, full detail on hover) with a
  deliberately long folder path.
