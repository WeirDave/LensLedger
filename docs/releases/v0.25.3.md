A concurrency bug that only became visible once yesterday's fix started
doing its job.

## `database is locked`, and why it only showed up now

Minutes after 0.25.2 shipped, running a real scan flooded the console
with `sqlite3.OperationalError: database is locked` on every status
request, and the Scan your photos page's live counters broke mid-scan.

The cause: `_configure_connection()` in `photo_index.py` unconditionally
ran `PRAGMA user_version=N` followed by a commit on *every* connection —
including the throwaway ones opened just to answer "how's it going?"
status checks, which the page polls across five endpoints every 700ms
during an active scan. That's a real write, competing for SQLite's single
writer slot, on a request that never needed to write anything.

This bug has probably always existed. It stayed invisible because, before
0.25.2, a scan run against this library finished in seconds — the
placeholder-detection bug meant it was skipping ~96% of the files, so
there was never enough sustained writing for the lock contention to
matter. The moment scans started doing real, minutes-long work, the five
polling connections and the active scan writer began colliding
constantly.

The fix: skip the `PRAGMA user_version` write entirely when the schema is
already at the target version, which is true for nearly every connection
opened after the first. Status checks are now genuinely read-only.

## Confirmed against the fix it depends on

Caught this live, mid-scan: 2,200 files in, 1,766 of them (80%) were
being correctly recognized as real, previously-wrongly-skipped files —
direct field confirmation that 0.25.2's placeholder-detection fix is
doing exactly what it's supposed to.
