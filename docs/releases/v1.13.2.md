## Why this release

Embedding tags in a photo sometimes needs a working copy. ExifTool refuses a
file whose extension does not match its contents, such as a PNG saved with a
`.jpg` name, and one whose name is too long for its temporary file. In those
cases LensLedger writes the tags into a short-named copy and then copies that
back over the photo.

The photo that copy was written back over was worked out by taking the last
item of the ExifTool command. Every place that writes tags put the photo
there, so no file was ever overwritten by mistake. The rule was still implicit:
a command that ended in anything else would have had that treated as the file
to replace.

## What changed

- The photo being tagged is now passed to the write step as its own value,
  and the ExifTool command is built from it. The working-copy step writes back
  to exactly that photo.
- Nothing changes for someone using LensLedger. Tags are written to the same
  files, in the same way, with the same safety copy and pixel check.

## Verified

- Full test suite: 265 tests, all passing.
- New test: with ExifTool stubbed to refuse the photo as a misnamed PNG, a
  write whose options end in the path of another existing file replaces the
  photo from the working copy and leaves the other file untouched. The working
  copy takes the `.png` type and is removed afterwards. The test fails if the
  write-back target is read from the end of the options again.
- The existing end-to-end tests with the bundled ExifTool still write tags into
  a PNG saved as `.jpg` and into a photo with a 250-character file name.
