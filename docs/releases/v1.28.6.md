# Jobs that write to photos no longer overlap, update and restore fixes

## Why this release

- Two publish runs, or a publish run and a tag run, could write to the same photos at once.
- Two requests to write all tags could both pass the "already running" check and each start a run.
- Opening another library while photos were being written switched the library underneath the job.
- A failed update restart could leave the update stuck as "restarting", and a restore left names marked as already published.

## What changed

### Jobs that write to photos

- **Publish** (the Publish page, **Publish all**) now refuses to start while another publish run is going, with the message "Publishing is already running". Its progress is reset when a run ends, including when it fails part way, so the page no longer waits on a run that is over.
- **Publish** also refuses while tags are being written, and **Write all tags** refuses while names are being published. Each says which one to wait for.
- **Write all tags** now claims itself in the same step that checks it is not already running. Choosing the photos and checking disk space take time, and two requests in that time could both start a run. If the run cannot start, for example because there is not enough disk space, the claim is released and the earlier status is restored.
- Opening another library (**Settings**, **Photo libraries**, or the reconnect page) is refused while tags are being written or names are being published, and does not record anything for the new library in that case.
- **Auto-classify photos after meaning search** now waits its turn behind a classification that is already running and skips itself, with a line in the log, instead of running at the same time. While it runs, it shows as a running classification and takes the same lock as **Classify photos**, so a second one cannot start beside it.

### Restore and people

- **Restore** from a safety copy (and putting back photos from an interrupted write) clears the published mark on the photo's confirmed names. The restored file no longer carries them, and they are offered again by **Publish all** instead of being counted as already written.
- Merging people no longer counts a photo that cannot carry names as rewritten, and undoing a merge or other people batch no longer fails on such a photo.

### Updates

- If the helper that installs a downloaded update cannot be started, the update stays available so that it can be tried again. It was left as "restarting", and the next attempt reported that no update was ready.
- If a git checkout has been updated but the helper that restarts LensLedger cannot be started, the update status shows an error that says the new version is installed and that LensLedger needs to be closed and started again.

## Not changed

- Scans, text recognition, meaning search and face detection are not affected by the new checks.
- Safety copies, publish results and tag contents are written exactly as before.

## Verified

- Full test suite: 531 tests, all passing.
- New tests start two requests against each other: a second publish while one is running, a second tag run while the first is still preparing, a tag run while names are published and the reverse, and opening a library during a tag run. They also cover the status after a failed publish or tag start, auto-classify with and without a classification running, update status after a failed helper start in both install types, published marks after a restore, and undoing a batch that includes a photo that could not carry names.
