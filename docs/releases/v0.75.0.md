## Motivation

After adding cohesion-based "confidence" percentages in v0.74.0, user feedback
made clear that cohesion (how consistent a person's photos are with each other)
is not the metric people care about. Users want to know: **when the system says
this is person X, how often is it right?** That's accuracy, not cohesion.

Additionally, the Name Faces page had a cycling bug: when a user unchecked
some faces in an "Also looks like" group and confirmed the rest, the unchecked
faces reappeared in the next round indefinitely.

## What changed

### Recognition accuracy on People cards

The People search page (`/?scope=people`) now shows each person's **accuracy
percentage** — calculated from the `people_review_actions` table as:

> confirmed / (confirmed + rejected + corrected) × 100

This answers the question "how often is the system right?" directly. People
with 100% accuracy have never had a wrong suggestion. A person at 87% means
the system occasionally suggests the wrong face for them.

Accuracy appears once at least one suggestion has been reviewed. If no
review history exists for a person, only the confirmed photo count is shown.

### Removed cohesion "confidence" from UI

The cohesion-based "confidence" percentage has been removed from user-facing
displays (match group headers and done banners in Name Faces). The internal
cohesion value is still computed and used for the "Confirm all remaining"
threshold check (≥75% cohesion + ≥25 confirmed faces), but users no longer
see the misleading label.

### User manual: Recognition accuracy section

Added a new "Recognition accuracy" section to the user manual explaining:
- What accuracy means (confirmed vs. total review decisions)
- How face recognition works (centroid model, similarity thresholds)
- The 65% suggestion threshold, 75% auto-confirm threshold
- When accuracy appears on person cards

Also added a "Confirm all remaining" section documenting the one-click
bulk confirmation feature from v0.74.0.

### Fixed cycling bug in Name Faces

When a user unchecked faces in an "Also looks like" group and confirmed the
rest, the unchecked faces reappeared in the next batch. This happened because
`find_more_faces` had no way to know which faces the user had already seen
and declined.

Fix: the JS now passes `exclude_face_ids` (the unchecked face IDs) to the
server, and `find_more_faces` skips those faces when building the next batch.
