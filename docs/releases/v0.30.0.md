Two more items from the same running feedback thread: the update panel
hanging on "Checking for updates…", and — after three separate attempts to
patch around it — the address-autofill popup on "Who is this?" still
showing up. The reporter's own words on the third attempt: *"you've given
it three shots and it's still not fixed."* This release replaces the
approach instead of patching it again.

## The autofill popup was never going to go away with autocomplete="off"

The first two attempts (v0.29.0's `autocomplete="off"` on all three
person-name fields) were the standard fix for this, and it works in most
browsers. It doesn't reliably work in Firefox: Firefox's Form Autofill
feature for addresses largely disregards `autocomplete="off"` on ordinary
text fields, by design, so a Firefox user typing a name into "Who is
this?" could still get a saved street address suggested over the person
list.

The fix that actually closes the gap is the same one the date picker
already proved: stop using a native form control the browser has any
opinion about. `web/js/person-picker.js` is a small shared widget — a
`<button>` trigger (buttons are never autofill targets, full stop) that
opens a popover with a live-filtered list of known people and a pinned
"+ New person" row. Typing narrows the list; pressing Enter on an exact
match chooses it; pressing Enter with no match — or clicking "+ New
person" — reveals a plain text field (carrying over whatever was already
typed) for the new name. Choosing an existing name or confirming a new one
submits immediately.

The same widget now backs all three real person-name fields in the app —
Name faces' "Who is this?", the main viewer's "Person's name", and People
review's optional correction field — replacing three separate
`<input list=peopleOptions>` combinations that all had the identical
exposure. A fourth instance existed only in an unreachable, dead code path
(an embedded review modal nothing in the UI actually opens); it was left
alone for now and flagged separately for removal rather than fixed, since
fixing dead code wastes the effort.

## The update panel that never finished checking

A smaller, unrelated bug surfaced in the same session: clicking "Check
again" on a source checkout's update panel would show "Checking for
updates…" and then simply stop — it never became "current" or "available".
The managed-install code path already re-polls every 500ms while a check
is in flight (`setTimeout(refresh, 500)`); the source-checkout /
extracted-ZIP branch of the same function never had that retry, so it only
ever showed whatever state happened to be true at the single moment it
first rendered. Added the same retry there.
