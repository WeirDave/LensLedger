## Why this release

1.14.0 dated photos from the camera data inside the file, but videos and
camera RAW files were left on the old rule: a date in the file or folder
name, or nothing. Camera videos (`MVI_1234.mov`) and RAW files
(`DSC01234.ARW`) are named without dates, so in a library with either, they
showed "Date unknown" and dropped out of the date filter, the
**◀ Day** / **Day ▶** buttons and **Newest first** / **Oldest first**.

## What changed

**Dates for videos**

- MP4, MOV, M4V and 3GP files are dated from the movie header.
- An iPhone video also records the local time it was shot, with its UTC
  offset. That day is used in preference to the header, which is UTC: a
  video shot at 9 pm on the 4th in California is dated the 4th, not the 5th.
- The order is: the local day the file records, then a date in the file or
  folder name, then the UTC day from the movie header. Other cameras record
  only the UTC day, so a late-evening video from one of them can be dated a
  day late unless its name carries the date.
- AVI, WMV, MPG and MKV videos are still dated from their names only.

**Dates for camera RAW files**

- DNG, CR2, NEF, ARW, ORF and RW2 are read from the date taken in the file's
  Exif block, then the date in its main directory.
- CR3 is read from Canon's Exif block inside the file, and RAF from the
  JPEG preview Fujifilm stores in it.
- A date inside the file is used in preference to one in the name.

**Re-dating**

- Libraries indexed by an earlier version are re-dated on their next scan.
  This reads only the first part of each file, no decoding, so it is much
  quicker than the one-time fingerprinting added in 1.17.0.
- A date that is clearly an unset camera clock (before 1971) or in the
  future is never used.

**Under the hood**

- The files are read directly (box headers and TIFF directories), not with
  the bundled ExifTool, so this behaves the same on every platform and
  starts no extra process per file.

## Verified

- 13 new tests covering: the UTC header date; a 64-bit header and a movie
  box stored after the media; iPhone local dates, with both layouts the
  `meta` box appears in; unset clocks; damaged, empty and looping files
  (no date and no error); the order local day, then name, then UTC;
  TIFF RAW variants in both byte orders including the ORF and RW2 headers;
  the file date used only when no date taken exists; RAF; CR3; a RAW
  header beating its file name; damaged RAW files; and a scan dating both
  kinds of file, re-dating a library that an earlier version had scanned.
- Each rule was checked to fail with it removed. Two checks first passed
  falsely: one mutation matched a stale compiled file, and two tests moved
  together with the thing they were testing. Both were fixed.
- **Limit of the checking:** the test files are built by hand to follow the
  published layouts. They were not checked against real camera files, because
  real photos cannot be committed. A camera that lays its file out
  differently will simply get no date from this change and keep the old
  behaviour.
