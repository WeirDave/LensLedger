## What happened

The v0.81.7 fix addressed faces resurfacing when identified from the photo viewer, but the root cause was structural: `asset_people` has a primary key of `(asset_id, person_id)`, so it can only store one `face_id` per person per photo. When the same person appears multiple times in one photo (common in composite/collage photos like photo booth strips), confirming the second face overwrites the first face's `face_id`, and the first face reappears as unidentified.

## What changed

Added a `person_id` column directly to `face_embeddings`. Each detected face now independently tracks whether it has been identified, regardless of how many times the same person appears in the same photo.

**Database**: Schema version bumped from 12 to 13. The migration adds the `person_id` column and backfills it from existing `asset_people.face_id` links, so all previously confirmed faces are immediately recognized.

**All confirmation flows updated** — `name_face`, `name_face_batch`, `add_person`, `find_more_faces` auto-confirm, `confirm_remaining_faces`, `_apply_people_review_decision`, and `face_learning.learn()` now set `person_id` on `face_embeddings` alongside the `asset_people` row.

**All exclusion queries simplified** — the `NOT EXISTS (SELECT 1 FROM asset_people ap WHERE ap.face_id=f.id ...)` subqueries throughout the codebase are replaced with `f.person_id IS NULL`, which is both simpler and correct for the multi-face case.

**Undo flow** — undoing a review action restores `face_embeddings.person_id` to match the previous state.

**Centroid queries** — the person-centroid building queries now read directly from `face_embeddings WHERE person_id=?` instead of joining through `asset_people`.
