## Motivation

The Name Faces page was always showing the same faces. The query pulled the
500 most recently inserted face IDs, then diversity-filtered those down to
~30. For a library with 50,000 unidentified faces, that meant 99% of the
library was invisible — the page only ever drew from the same 1% (typically
one event or folder that happened to be scanned last).

A user with a 20-year photo library scanning for the first time would see
faces only from whatever folder was indexed last, never getting a chance to
name people from earlier decades.

## What changed

- The face pool query now uses `ORDER BY RANDOM()` instead of
  `ORDER BY face_id DESC`, so each visit to the Name Faces page surfaces
  a different random sample from the entire library.
- The pool size was increased from 500 to 2,000 for better diversity
  coverage in large libraries. The `min(total, 2000)` guard means small
  libraries (under 2,000 unidentified faces) simply load everything —
  no sampling needed.
- The diversity filter (cosine similarity threshold of 0.78) and one-face-
  per-photo constraint remain unchanged — the page still shows varied
  people, just from a much broader and randomized slice of the library.

## Performance note

Loading 2,000 face embeddings (~4 MB) and running the diversity sampling
(~60,000 dot products in the worst case) completes in milliseconds on any
machine. The `ORDER BY RANDOM()` on the full qualifying set is handled
efficiently by SQLite. No adaptive scaling is needed.
