## Why this release

v1.4.0 made every action appear in the log. A sweep afterwards for actions that
report an outcome found several that still did not, and the most serious of
them delete photos.

Emptying the Review Bin removes the photo file and its database entry in the
same step. Nothing else anywhere holds a record of what was there. Until now it
also wrote nothing to the log, so a permanent deletion of any number of photos
left no trace at all of which ones.

## Actions that touch photo files

These now name every photo they act on:

- **Moving photos to the Review Bin**, one at a time or in bulk, records each
  file as it leaves the library and how many moved in total.
- **Restoring from the Review Bin** records each file put back.
- **Deleting from the Review Bin**, and **emptying it**, record each file as it
  is deleted permanently, and how many went. A file that had already vanished
  is reported separately rather than counted as deleted.

## Other actions that now report what they did

- **Merging two people** — how many names were folded in, how many photos were
  updated and how many were rewritten.
- **Adding people to a group** and **removing them**, including when the group
  turned out to be empty.
- **Adding tags in bulk** — how many tags across how many photos.
- **Showing skipped faces again** — how many came back into review.
- **Undoing a batch of review decisions** — how many were undone.
- **Exporting and importing the database** — the file used and the photo count.
- **Setting up meaning search or face detection** — that the install started,
  and whether it finished or failed. These run for up to half an hour and said
  nothing at all before, during or after.
- **"Write all tags" with nothing to write** now says so. It logged the request
  and then went quiet, which is indistinguishable from a run that died.

## A completed scan reported as failed

After indexing photos, LensLedger saves a note of which library is open. If
that note could not be written the whole scan was reported as failed, even
though every photo had been indexed correctly.

Two changes:

- Saving that note can no longer fail the scan. The failure is reported on its
  own terms, and the scan result stands.
- Files that record settings, the known libraries and their databases are now
  written with a short retry. Replacing a file fails outright on Windows if
  anything else holds it open even for a moment, which cloud sync and virus
  scanners both do routinely. A brief retry turns a hard failure back into the
  momentary contention it actually is, and a write that genuinely cannot
  complete no longer leaves a partial file behind.

This was found by reading the log after the changes above — the scan reported a
failure that the log then explained. It is the kind of fault that the previous
release's work exists to surface.

## Verified

- Full test suite: 164 tests, all passing, on Python 3.12.10 — up from 160.
- A new test checks that every action which moves or deletes a photo names the
  photo rather than only counting it, and fails if one stops doing so.
- Three new tests cover the retrying write: that it retries rather than failing
  at once, that it gives up cleanly without leaving a temporary file behind,
  and that a scan is not discarded when saving the library note fails.
- Checked against a library of generated test images: photos moved to the
  Review Bin and then permanently deleted, with each file named in the log at
  both steps, and a scan that now completes rather than reporting a failure.
