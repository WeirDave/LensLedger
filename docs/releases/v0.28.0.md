Direct user feedback, again the same day: the update panel told a real git
checkout it was "run directly from an extracted download" and to run
`Install LensLedger.cmd` — even though the folder in question was this exact
repo, already sitting on the latest commit.

## The process was lying, not the detection

The confusion had a precise cause. `is_source_checkout` — added a few
releases back specifically to give source checkouts the right message — was
computed correctly. The bug was one level up: the running Python process's
`APP_VERSION` is imported once, at startup, and stays frozen in memory for
as long as that process lives. `git pull` (or any other on-disk edit)
changes `product.py`, but nothing tells the *already-running* process about
it. A browser hard-refresh only re-fetches `web/js/*.js` and `*.css` — it
can't reach into the Python process and reload its imports.

So the reporter's server was still running an old version from before
`is_source_checkout` existed at all — hence the wrong message. The README
already explained this ("backend changes need the process restarted, front-
end changes just need a refresh"), but the app itself gave no sign that this
was the problem. The reporter's own diagnosis, once we looked at it
together: *"if the update code is checking the code that it's running from
against the code that's on GitHub... it should know the code in the
directory is current, and give you an option to restart."*

## Comparing the process against its own disk

`update_status` now reads `product.py` fresh off disk on every check
(`_on_disk_app_version` in `photo_search.py`) and compares it against the
`APP_VERSION` baked into the running process. This is a different check
from the existing GitHub comparison — "is the running process behind the
code already sitting in this folder" versus "is this folder behind the
latest published release" — and both can be true independently. When the
process is behind its own disk, the panel now says so plainly ("LensLedger
X.Y.Z is on disk, not running yet") and offers **Restart to apply**.

Restarting is deliberately not the existing install flow. There is no
download, no verification, no file replacement — `restart_source` in
`photo_search.py` spawns the same wait-for-old-PID-then-relaunch helper the
managed-install path already uses (`lensledger_updater.py`'s new
`restart-source` subcommand, built on the existing `wait_for_process` /
`launch_lensledger`), but skips every step that touches files. It just
gets the same process running again with what's already on disk.

## Verified

- Full automated suite (68 tests, three new — a server test proving
  `restart_ready` flips true only when the on-disk and running versions
  disagree, a server test proving the restart endpoint transitions state
  without spawning a real process, and an updater test proving the CLI
  dispatch waits for the old PID then relaunches with no file changes)
  green.
- Manually verified live: cloned the repo to a disposable folder, started
  LensLedger from it, then edited its `product.py` on disk without
  restarting the process — confirmed `/api/update/status` correctly
  reported `restart_ready: true` with the stale running version and the
  new on-disk version; confirmed the update panel rendered "LensLedger
  ...is on disk, not running yet" with a visible "Restart to apply" button
  and the old "Download, install & restart" button correctly hidden.
  Deliberately did not click the live restart button in this pass — the
  spawn-and-relaunch mechanics are covered by the mocked automated tests
  instead, since a real relaunch from a throwaway clone risks colliding
  with a real LensLedger instance already bound to the default port.
