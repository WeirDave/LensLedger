# Sidecar files no longer overwrite other programs' files or each other

## Why this release

- Writing a sidecar replaced any `.xmp` file already next to the photo, including one created by a program such as Lightroom, which holds that program's own settings.
- `IMG_0001.jpg` and `IMG_0001.cr2` both use `IMG_0001.xmp`, so each write replaced the tags the other had put there.
- The sidecar was written in place, so an interruption could leave an empty or partial file.
- A **Write all tags** run that stopped on an unexpected error stayed "running" in the status.

## What changed

### Sidecar files

- **Write all tags** and writing tags to a single photo no longer replace an `.xmp` file that another program created. The photo is listed under "photos could not carry everything" on the Publish page, with the reason, and the file is left as it was. When the photo is also embedded (write mode "Both"), the photo itself is still written and is recorded as embedded only, so the sidecar is tried again on the next run once the other file is gone. For a single photo with sidecar-only writing, the request is refused with the same reason.
- When several pictures share one sidecar name, one of them owns it. The picture that cannot carry tags itself (a RAW file, GIF or BMP) owns it; among equals the first name alphabetically does. Videos are not counted. The other pictures are listed under "photos could not carry everything" with the name of the owner, and are not written to the shared sidecar.
- A sidecar is written to a temporary file in the same folder and swapped in whole. An interruption leaves the earlier sidecar in place, and no temporary file is left behind.
- An empty sidecar, such as one left by an earlier interrupted write, is replaced. A sidecar that cannot be read as text is treated as another program's and left alone.

### Write all tags

- A run that stops on an unexpected error now ends in an error state with a message such as "Writing tags stopped part way: ...", keeps the counts reached so far, and allows a new run. It stayed "running" before, which blocked the next run until LensLedger was restarted.

## Not changed

- Sidecars LensLedger wrote itself are still replaced when tags change.
- Moving LensLedger's own sidecar aside when a file type's sidecar box is turned off works as before, and still leaves other programs' sidecars and shared ones alone.
- **Publish all**, merging people and the single-photo publish in the viewer are not changed.
- Embedded writes are not changed.

## Verified

- Full test suite: 542 tests, all passing.
- New tests cover: another program's sidecar being left alone in both batch and single-photo writes, an unreadable sidecar, an empty sidecar being replaced, an interrupted write leaving the earlier sidecar and no stray file, the ownership rule for RAW, GIF, equal names and videos, a JPEG not overwriting its RAW file's shared sidecar, a photo still being embedded when only its sidecar is refused and the sidecar following on a later run, and a crashed run ending as an error and allowing a new one.
