## Motivation

When a library root folder or subfolder was renamed at the OS level, LensLedger lost all enrichment data (tags, people, face embeddings, OCR text, review history) for affected photos. The database filename was derived from a hash of the root path, so a renamed root created an entirely new empty database. Within a library, subfolder renames caused files to appear as new entries while old-path records were cascade-deleted.

For users who reorganize their photo folders, this meant potentially hours of face training, tagging, and OCR work were silently lost.

## What changed

### Content-hash reconciliation (subfolder/file renames)

During a library scan, LensLedger now computes a fast content fingerprint for each file: SHA-256 of the first 8 KB plus the file size (24-character hex string). This is stored in a new `content_hash` column on the `assets` table.

When orphan detection finds files in the database that no longer exist on disk, it now checks whether any newly-discovered files share the same content hash. If a match is found, the old record's paths are updated in place — preserving the asset ID and all associated enrichment data (tags, people assignments, face embeddings, OCR text, semantic embeddings, review history, annotations). Only genuinely deleted files are removed from the database.

### Stable database filenames (root renames)

The `library-state.json` file now stores a `db_mappings` section that maps library root paths to their database filenames. When a library is opened, this mapping is recorded. If the root folder is later renamed at the OS level, the user can re-associate the new path with the existing database through the settings page.

A `library_metadata` table has been added to the database schema, storing a persistent `library_id` UUID that uniquely identifies each library database independently of its filesystem path.

### Schema changes

Database schema bumped from version 11 to 12:
- New `content_hash TEXT` column on `assets` (defaults to empty string; populated on next scan)
- New `library_metadata` table with key-value storage (auto-populated with a `library_id` UUID on first connection)

## Verified

- Test suite: 79 tests passed.
- Schema migration is idempotent — existing databases upgrade cleanly on next connection.
