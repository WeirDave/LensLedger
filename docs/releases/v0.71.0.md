## Motivation

With continuous face matching (v0.70.0), the "Also looks like" flow can now
chain through hundreds of matches per person. But at 50 faces per round, with
each face confirmed via its own HTTP request, processing a person who appears
in 1,000 photos would take 20 rounds of 50, each round making 50 sequential
API calls. That's painfully slow for large libraries.

## What changed

### Batch confirmation endpoint — `/api/faces/name-batch`

A new POST endpoint accepts a `person_id` and an array of `face_ids`, then
confirms all of them in a single database transaction. Each face gets:
- An `asset_people` row with `state='confirmed'` and `source='manual_face'`
- Person tags synced and search row rebuilt
- JPEG metadata published with the person's name

Faces that no longer exist or belong to trashed photos are silently skipped.
If any exception occurs mid-batch, all metadata writes are rolled back via
`_restore_people_batch`.

### Match limit raised from 50 to 200

Both `_find_similar_unidentified_faces` (used on initial naming) and
`find_more_faces` (used for continuous chaining) now return up to 200 matches
per round. With batch confirmation, 200 faces confirm in one request instead
of 200 sequential round-trips.

### Frontend uses batch endpoint

The "Confirm all" button now collects all checked face IDs and sends them in
a single `/api/faces/name-batch` call, then chains into `/api/faces/find-more`
as before. The sequential per-face loop is gone.

## Verified

- **Test suite**: 80 tests, all passed.
- Batch endpoint correctly confirms multiple faces in one transaction.
- Match groups now show up to 200 faces per round.
- Frontend sends one batch request instead of N sequential calls.
