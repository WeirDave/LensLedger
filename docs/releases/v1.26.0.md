# Launcher opens as a Windows Terminal tab

## Why this release

Starting LensLedger from `Start LensLedger.cmd` always opened a console window of
its own. For someone who already keeps a Windows Terminal window open, that is one
more window to find, and every restart that had to start a new launcher opened
another. The same idea was already working in another app of the same family, so
this brings it here in the same shape.

## What can and cannot be done

Windows has no way to move a running process into a shell that is already open, so
"attach to the PowerShell I have open" is not on offer. What exists is
`wt.exe -w 0 new-tab`: a tab in the most recently used Windows Terminal window, or
a new Windows Terminal window when none is open. That is what this does.

## What changed

- `Start LensLedger.cmd` runs `python -m tools.terminal_tab "<launcher path>"`
  before anything else that can fail. The helper uses only the standard library and
  prints nothing. Exit code 0 means a tab now runs the launcher and this window
  exits cleanly; exit code 1 means run here.
- The tab runs `cmd.exe /c "<launcher>" --in-tab`. The launcher recognises the flag
  and skips the helper, so it can never open a second tab from inside the first.
  The server accepts and ignores `--in-tab`, because the launcher passes its
  arguments on.
- The launcher stays in its own window, with no tab opened, when any of these hold:
  - this is not Windows (macOS and Linux are untouched);
  - it is already inside Windows Terminal (`WT_SESSION` is set), which also covers
    the launcher being typed into an open PowerShell tab, and Windows Terminal set
    as the default terminal;
  - it is inside another terminal host such as VS Code (`TERM_PROGRAM` is set);
  - the tab's own `--in-tab` flag is present;
  - the setting is off;
  - `wt.exe` is not on the path;
  - the launcher's path contains `;`, which Windows Terminal reads as a command
    separator;
  - starting Windows Terminal raises an error. The reason is written to the
    LensLedger log and the launcher carries on in the current window.
- **Settings → Photo libraries → Open the launcher in a Windows Terminal tab** turns
  it off. It is on by default and stored as `startup.terminal_tab` in
  `settings.json`. The helper reads it before the server exists, through the same
  settings loader as the server, and treats an unreadable settings file as on. A
  settings problem never stops the launcher.
- `tools/terminal_tab.py` and a new `tools/__init__.py` are part of the release ZIP
  and required by the updater, so an update that lacks them is refused. The empty
  package file makes `tools` an ordinary package, so no other `tools` module on the
  path can take its place.

### Restarts

- Version 1.25.0 made **Restart server**, **Restart now** and installing an update
  start the server again in the same window (exit code 75 means "start again here"
  to the launcher). That already keeps the tab, never opens a new window and never
  kills the old launcher, so it is unchanged. Inside the tab this release opens,
  the same loop runs in that tab.
- Where a restart does have to start a launcher of its own (an older copy of
  `Start LensLedger.cmd`, or the first launch after an install), it now opens that
  launcher as a tab, when the setting is on and `wt.exe` exists, and passes
  `--restarted` through so the browser is not opened again. The old window is not
  force-closed: an older launcher exits by itself on code 75, and Windows Terminal
  closes a tab after a clean exit but keeps one open after a killed `cmd.exe`.
  When no tab opens, the previous behaviour (a console of its own, then closing the
  old window) is unchanged.

## Not verified

**Nobody has run this on a real Windows Terminal yet.** The development machine
runs Linux, and `Start LensLedger.cmd` and `wt.exe` cannot run there. Two things
need checking by hand on Windows:

1. **How `wt.exe` parses the command line.** The tab command is
   `wt -w 0 new-tab --title LensLedger --suppressApplicationTitle -d <folder> cmd.exe /c "<launcher>" --in-tab`.
   The launcher path normally contains a space (`Start LensLedger.cmd`), and
   `cmd.exe /c` has its own quote rules, so confirm the tab starts the launcher
   with no error and the server starts.
2. **That the old tab closes on the clean exit.** After a restart through the
   helper, the previous tab should disappear by itself rather than stay open with a
   "process exited" message.

Also worth a look: double-click `Start LensLedger.cmd` with Windows Terminal open
and with none open; start it from a PowerShell tab (it must run in that tab); start
it with the setting off; and rename `wt.exe` out of the way.

## Verified

- Full suite on Linux: 461 tests, 5 errors, 30 skipped. The 5 errors are the
  publish and People tests that run the Windows `ExifTool.exe`, which cannot run on
  Linux; they error the same way without this change. The other 426 ran and passed.
- 28 new tests in `tests/test_terminal_tab.py` and one in `tests/test_server.py`:
  the hand-off decision across every reason to stay (operating system, both
  terminal variables, the tab flag, the setting, no `wt.exe`, a `;` in the path);
  the exact tab command, argument by argument; Windows Terminal failing to start
  giving "run here" and a log line instead of a crash; the restart opening a tab
  with no console and no window kill, and falling back unchanged when no tab opens;
  the setting round-tripping through the real settings loader with an unreadable
  file leaving it on; the Settings page showing the checkbox from the saved value
  and the page's own save script sending it back (run under Node); and the server
  accepting `--in-tab`.
- Each guard was removed once in turn (27 changes to the helper, the restart, the
  settings page, the save script, the default and the update's required files), and
  every one turned a test red.
- The Settings page was driven in Chromium in the light and dark themes against a
  generated test library: the toggle is on by default, saves off and on, and the
  saved value is shown again after a reload.
