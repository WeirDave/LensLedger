# Publish failures explained, Repair fixed, People groups ordered

## Why this release

Three things in 1.23.0 did not hold up on a real library.

- **The People page order.** 1.23.0 promised the biggest groups of unnamed faces
  first. On a library of 36,000 unnamed faces the "+N similar" badges came out of
  order. Groups were ranked by their size within a random sample of 3,000 faces,
  but the badge shows the size across the whole library. With only about one face
  in twelve sampled, a real group of 33 and a real group of 14 can both look like
  3.
- **Publish failures.** When 9 of 308 photos failed to publish, the page showed
  raw messages from ExifTool and Windows, offered a **Repair** button on eight of
  the nine, and had no way to copy the list.
- **The cutoff report.** The instructions gave a path with placeholders in it,
  and running it as written failed with a "No catalogue" error.

## What changed

### People groups, biggest first

- The page now finds three times as many candidate groups as it needs, measures
  each one against all unnamed faces (up to 50,000), and orders them by that real
  count. The count shown in the badge and the order now agree, and a bigger group
  that the sample had split or underrated is no longer missed.

### Publish failures

- Each failure now carries a plain-language line under the raw message:
  - a leftover ExifTool temporary file (`..._exiftool_tmp`) that must be deleted
    before the photo can be written again;
  - a file Windows would not let LensLedger replace (rename or permission errors),
    which usually means sync, a preview pane or antivirus has it open;
  - a failed picture check, where LensLedger put the original back so the photo is
    as it was;
  - damaged picture data;
  - a file type that cannot carry names.
  A message LensLedger does not recognise is shown as before, without a line.
- **Copy list** buttons were added to the failure list after a people metadata
  publish and to each group in the Write all tags report. They copy every failed
  photo (not only the first 50 shown) as "path — reason", one per line. The text
  contains real paths, so keep it private.

### Repair

- **Repair is offered only where it can help:** a JPEG whose picture data is
  damaged or failed the picture check. It is not offered for temporary-file or
  file-in-use errors, because re-saving the picture cannot clear them and only
  costs quality, and never for HEIC or HEIF.
- HEIC and HEIF were removed because Repair always wrote JPEG data, so repairing
  one would have left JPEG data in a file named `.heic`. The server now refuses a
  repair of anything but a JPEG, whatever the page shows.
- **Repair never worked on a JPEG.** It asked Pillow to keep the original's
  compression settings from a converted copy, which Pillow refuses, so every
  attempt ended with "Cannot use 'keep' when original image is not a JPEG" and
  the original put back. It now saves the decoded original and keeps its
  compression settings, EXIF, colour profile and XMP. A backup is still made first.
  IPTC fields are not carried over.
- A re-save is still lossy. The hint says so.

### Cutoff report

- Run `python src\face_threshold_report.py` with no arguments and it uses the
  catalogue of the library LensLedger last opened, the same one the app opens.
  `--db` still works. If the value is the placeholder from the old instructions,
  the report says so instead of failing with "No catalogue".

### Updater

- `publish_failures.py` is part of the release ZIP and required by the updater.

## Fixed during testing

- The first test of Repair on a JPEG failed with the Pillow error above. That
  showed Repair had never worked, which went beyond restricting when it appears.
- In the browser the hint text broke in the middle of words, because the table
  cell it sits in breaks anywhere so that long file paths wrap. The hint now
  breaks at word boundaries.
- Checking the copy button, one run read the button before the copy had finished.
  The copy was correct, so this was the check and not the button, and the check
  now waits for the "Copied" label.

## Measurements

On generated test data, as in 1.23.0 (invented identities, no real photos): 36,000
faces in 400 uneven groups, first 30 cards.

| | 1.23.0 | 1.23.1 |
|---|---|---|
| Badge order | out of order in 9 places, e.g. 338, 316, 369, 445 | never increases down the list |
| Photos belonging to the people shown | 19,031 | 19,157 |
| Time to build the page | 1.54 s | 1.33 s |

## Known limits

- The failure lines are chosen by matching the wording of the error. A message
  that matches none gets no line and no Repair button, even if Repair could have
  helped. Tell me the message and it can be added.
- LensLedger does not delete leftover `_exiftool_tmp` files or clear read-only
  flags itself. The hint says what to do.

## Verified

- Full test suite: 418 tests. 5 of them (publishing tests in `test_server.py`)
  error on the Linux machine this was developed on because the bundled
  `ExifTool.exe` is a Windows program. They error identically on 1.23.0. The other
  413 ran: 383 passed and 30 were skipped.
- New tests cover the real-count ordering (a sample that ranks the biggest group
  last, and counts never increasing down the list), every failure kind and which
  of them can be repaired, Repair refusing HEIC, HEIF and TIFF and leaving the
  file alone, Repair keeping EXIF and XMP on a JPEG, Repair turning a truncated
  JPEG into one that decodes completely, and the report finding the saved library,
  running with no arguments, and explaining the placeholder.
- Removing the re-sort made four of the ordering tests fail, and restoring it made
  them pass.
- The Publish page was driven in Chromium in the light and dark themes with a
  failure list built by the real classifier from invented paths: Repair appeared
  on exactly the two repairable JPEGs, seven rows had a hint, and the copied text
  was the nine expected lines.
