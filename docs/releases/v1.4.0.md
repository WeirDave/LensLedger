## Why this release

The log did not record what LensLedger was doing. Pressing "Fill in missing"
produced nothing that named the action, so there was no way to tell whether it
had run, how far it had got, or what it had touched. A run that found no work
ended in complete silence, which is indistinguishable from a run that never
started.

That matters more here than in most programs. LensLedger reads and writes
personal photos. Writes are copied, verified and reversible, but none of that
is any use to someone who cannot tell what happened. Silence during an
operation across tens of thousands of photos is the worst available default.

This release makes the log a real account of the program's behaviour, and adds
the disk-space and retention controls that a library-wide write needs before it
is safe to run.

## Everything the program does is now in the log

**Every action is named when it starts,** with its scope. The three
meaning-search buttons are told apart, so the log says "Fill in missing" or
"Re-scan everything" rather than a generic scan. Text recognition says whether
it is reading new photos or re-reading ones already done. Writing tags says how
many photos and which write mode.

**Every action reports an outcome,** including when there was nothing to do:

```
Meaning search: requested — Fill in missing, every photo with no meaning
   data, including ones an earlier run could not read
Fill in missing: started — every photo with no meaning data, including ones
   an earlier run could not read
Fill in missing: loading the ViT-L-14/openai model…
Fill in missing: model ready, looking for photos to index
Fill in missing: no photos need indexing
Fill in missing: finished in 3s — nothing needed indexing
```

Loading the model is now logged too. It can take a while on a cold start, and
that wait used to happen in silence, which is what a run with nothing to do
looked like from outside.

**Long-running work logs progress and elapsed time,** so a scan across a large
library shows movement. **Every file that cannot be processed is named, with
the reason.** Progress lines are rate limited; failure lines never are. A file
that fails silently is how a photo ended up marked as failed and skipped by
every later run.

**Automatic background checks are labelled as such,** so scheduled work is
distinguishable from something started by hand, and a check that skips because
a scan is already running says so rather than doing nothing visibly.

**Actions that do not go ahead are logged with the reason** — a rejected input,
a conflicting job, a missing file.

### It can no longer go quiet by accident

Every state-changing request is logged centrally, by the name of the button
that causes it, rather than each part of the program being relied on to
remember. Seventy-one actions are named. Six are deliberately quiet because
they only read state: browsing for a folder, previewing a publish, revealing a
file, checking for updates, and two development helpers.

A test fails if a new action is added without either naming it or listing it as
deliberately quiet, so this cannot silently regress.

### Two log robustness fixes

The log uses em dashes and ellipses. A real console handles them, but a
redirected or captured stream falls back to the system code page, where writing
one raises an error — which would have taken down the job the line was
describing. The log now asks for UTF-8, falls back to plain characters if it
cannot have it, and never lets a failure to write a line stop the work.

### A note on privacy

The log records real folder names and photo paths, because naming the file that
failed is the point of it. It is written to the per-user application data
folder, never beside the program, and each session now begins with a line
saying the file contains personal paths and should be edited before being
shared anywhere public. The per-request lines describe only the scope of an
action — never names, subjects or paths from the library.

## Before writing tags across a library

**A disk-space check.** Embedded writes keep a complete copy of every photo
they touch, so writing tags across a library needs room for a second copy of
everything it writes. The run now adds that up first and refuses before
starting if it will not fit, saying how much is needed, how much is free, how
far short it is, and the ways out — clear old copies, free space, or switch to
sidecar mode, which copies nothing.

**Retention limits,** in Settings under "Metadata publishing":

- **"Keep photo safety copies for (days)"**, default 30. 0 keeps them forever.
- **"Total size limit for safety copies (GB)"**, default 20. 0 means no limit.

Copies past either limit are cleared automatically after each run, oldest
first.

**A place to see and clear them.** The Scan your photos page has a new "Photo
safety copies" panel under "Backups", showing how many copies exist, how much
space they use and how much is free, with **"Clear copies past the limit"** and
**"Clear all safety copies"**. The photos themselves are never touched by
either.

## Other corrections to writing

- **Interrupted writes are detected.** If LensLedger stops mid-write, the
  affected photos are listed by name on the Scan your photos page, saying
  whether the original can still be put back.
- **Safety copies are verified by their contents,** not by file size alone. A
  copy that was the right size but the wrong bytes used to pass.
- **Photos stored online only are refused** with an explanation, rather than
  being attempted.
- **Settings are read from and written to the right place** when the data
  folder is set after startup. The location was previously fixed the first time
  the program touched it.

## Fixed during testing

**Settings could be written to the wrong file.** The settings location was
resolved once, when the program first loaded, so anything that changed the data
folder afterwards still read and wrote the original. This was found when the
test suite began failing in a way that only appeared in a full run: one test
was reading a value another had written, because both had reached past their
own temporary folders. The location is now resolved each time it is needed.

**A redundant status line.** The automatic check repeated the outstanding-work
summary that the location scan had already logged a moment earlier.

## Verified

- Full test suite: 156 tests, all passing, on Python 3.12.10 — up from 125.
- Sixteen new tests cover the action log: that an action logs when it starts,
  that one which does nothing still reports an outcome, that failures name the
  file and reason, that failures are never rate limited away while progress is,
  that an outcome is reported exactly once, and that an action used as a
  context manager always reports even when it raises.
- A test walks every state-changing route in the program and fails if one is
  neither named nor explicitly listed as deliberately quiet, and a second fails
  on labels left behind for routes that no longer exist.
- Tests confirm the per-request log lines contain no names, subjects or paths,
  that the log file lives outside the repository, and that the privacy notice
  is written.
- Tests confirm a log line that cannot be encoded does not stop the work, and
  that em dashes reach the file intact.
- Nine tests cover the safety-copy housekeeping: usage counting, clearing by
  age, clearing oldest-first to fit a size limit, limits set to zero meaning no
  limit, clearing everything, the space check refusing an impossible run, the
  size estimate tolerating a missing file, and a content check rejecting a
  same-size copy that a size check would have passed.
- Six tests cover the write path: that a finished write records finishing, that
  one which never finished is reported, that a rolled-back write leaves nothing
  behind, that a corrupted safety copy is rejected, that a library-wide write
  refuses when there is no room, and that an online-only photo is refused with
  a plain reason.
- Checked in a browser against a library of generated test images, in both
  light and dark themes: the "Photo safety copies" panel, the retention fields
  in Settings, and the log output from a full pass — re-scan everything, write
  all tags, clearing safety copies, and a rejected tag.
